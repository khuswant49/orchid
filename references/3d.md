## 1. The gate

Motion and 3D help when they **represent** something: a product to inspect, a place to explore, a process unfolding, spatial structure, a body of work. When animated and static graphics carry the same information, animation generally doesn't help (Tversky et al. 2002). Representational, realistic animation does (Höffler & Leutner 2007: d = 0.40 representational, 0.76 realistic). Interesting-but-irrelevant material placed first hurts comprehension — the seductive-details effect (Harp & Mayer 1998). A decorative 3D object at the top of a page is the textbook case.

Before any 3D, write in `.orchid/3d.md`:
- **Subject:** what it shows that a still image can't (rotation, assembly, scale, sequence, exploration).
- **Visitor's gain:** what they understand or can do because of it.
- **Cost:** library + asset weight, and the effort.

No subject → no 3D. "Looks premium" is not a subject. A great typographic page with no 3D beats a blob.

The gate covers the setting as well as the object. A 2026 meta-analysis (50 experiments) confirmed that irrelevant material costs comprehension through extra cognitive load, and a 2026 experiment found that even a realistic picture of the right subject hurt learning when it sat in a rich, irrelevant background (see `psychology.md` §10). So: a plain, lit stage or a setting that belongs to the subject; no decorative environments, skyboxes or particle fields around a product. Accent shaders (§3, "Responsive surface") stay small and quiet, and stop under reduced motion.

## 2. Choosing the level and the stack

| Level | When | Default stack |
|---|---|---|
| **None** | Most operate and read pages; any page without a subject | — |
| **Accent** | One small scene or a single shader that supports the message (a product turning, a subtle surface that responds to the cursor, a data form) | One full-screen or contained shader → **OGL** (13 KB gzip). A small object → **React Three Fiber** |
| **Full scene** | The subject *is* spatial or the experience is the point (product viewer, place flythrough, interactive work gallery, a game) | **React Three Fiber 9 + drei 10** on three.js's WebGL renderer |
| **Scroll-scrubbed frames** | A cinematic moment that video captures better than real-time 3D | `templates/three/ScrollSequence.tsx` (see motion.md) |
| **User-supplied Spline scene** | Only when the user designed it in Spline | `@splinetool/react-spline`; budget for its ~570 KB runtime |

Measured weights (gzip): three.js minimal scene 130 KB; whole library 184 KB; `three/webgpu` 289 KB; OGL 13 KB; Spline runtime 572 KB before the scene file.

**Why WebGL, not WebGPU, by default:** WebGPU ships in all major browsers but not Linux or Firefox on Android, and three.js still calls `WebGPURenderer` experimental. It doesn't run custom GLSL (`ShaderMaterial`, `onBeforeCompile`) or `@react-three/postprocessing`, and agents' training data is mostly GLSL, so error rates rise. Use WebGPU only when the user asks or a feature needs compute (millions of particles).

**React Three Fiber v10** has been in alpha through 2026 (v9 is the stable release for React 19). It moves to node materials and TSL shaders, and on WebGPU, GLSL-based helpers (many drei shader materials, `@react-three/postprocessing`) don't run. Stay on v9 + drei 10 until v10 is stable; when you do adopt it, check its migration guide for which entry point keeps the WebGL renderer, and write shaders in TSL. In TSL, plain JavaScript `if`/`for` run once while the node graph is built; branching on the GPU needs TSL's `If()`, `Loop()` or `select()`.

## 3. Recipes

Each recipe passes the gate when the subject is real. Start from `templates/three/`:
- `OrchidScene.tsx` — the light shell: server-rendered poster, near-viewport mounting, GPU tier, reduced motion, DOM mirror. It lazy-loads `SceneCanvas.tsx` (three.js, R3F, drei), so three.js isn't in the initial page load (verified: ~885 KB of JS deferred until the scene nears the viewport).
- Put scene contents in their own file and `lazy()`-import them too (see `WorkGallery.example.tsx` + `WorkGallery.planes.tsx`).
- `tokens.ts` — `tokenColor('primary')` reads design tokens for materials, since three.js can't parse `oklch()`.
- `ScrollSequence.tsx` — scroll-scrubbed frames; props are plain data, so it works from Server Components.

| Recipe | Subject | Notes |
|---|---|---|
| **Product viewer** | A product the visitor would inspect | glTF model, `OrbitControls` with limits, `Environment` from a Poly Haven HDRI, `ContactShadows`, rotate on drag; keyboard buttons for rotate/zoom; poster = a good render |
| **Work gallery** | The user's own projects | Screenshots as textures on planes in a gentle arc or stack; scroll or drag moves through them; click opens the real case study (DOM). Captions in HTML |
| **Device turn** | A site or app the user built | A simple laptop or phone model with the user's screenshot as the screen texture, turning once on load or with scroll. Or use scroll-scrubbed frames |
| **Place flythrough** | A real location | Terrain from height data or a photogrammetry asset, fog, a scroll-driven camera on a spline path; never auto-play long movement |
| **Data form** | Data that is genuinely spatial or volumetric | Instanced meshes driven by real data; labels in HTML; a table equivalent in the DOM |
| **Responsive surface (accent)** | A material from the direction's referent (paper grain, ink, glass, water, metal) | One fragment shader on a plane behind or beside the headline; reacts slowly to the cursor; static under reduced motion |
| **Particles that mean something** | A shape tied to content (links forming their icon, data points) | Never ambient starfields. On Igloo Inc, particles swirl into a shape for the selected link |

**Single HTML file (no React):** keep the same structure by hand — an `<img data-orchid-poster>` inside a `data-orchid-3d` container; an `IntersectionObserver` that runs `await import('https://cdn.jsdelivr.net/npm/three@0.186.1/build/three.module.js')` (or a local module) only when the container nears the viewport; `matchMedia('(prefers-reduced-motion: reduce)')` keeps the poster; expose `window.__scene = { info, probes }` the same way so `check-page.mjs` can test it.

Crafted 3D shares four habits (Lusion's Oryzo, Abeto's Igloo Inc): one subject in view throughout; one consistent world across sections; grey-box planning before art; real-time rendering over video where possible to keep files small.

## 4. Performance budget

| Area | Budget |
|---|---|
| Device pixel ratio | `dpr={[1, 2]}` (R3F's default); tier 1–2 GPUs capped at 1.5 or 1 |
| Draw calls | Under 100 per frame; instancing for repeats |
| Lights | 3 or fewer; prefer an environment map plus one directional light |
| Shadows | Contact shadows or baked; real-time shadow maps 512–1024 px mobile, 1024–2048 desktop |
| Textures | KTX2 (Basis), ≤ 2048 px (≤ 1024 px mobile). VRAM ≈ w × h × 4 bytes + ⅓ for mipmaps: 2048² ≈ 21 MB, 4096² ≈ 85 MB |
| Geometry | Draco or Meshopt compression via `npx @gltf-transform/cli optimize in.glb out.glb --texture-compress ktx2` |
| Frame time (p95) | 16.7 ms desktop; 33 ms on throttled mobile |
| Render loop | `frameloop="demand"` for scenes that only change on interaction; pause when offscreen |
| Loading | Canvas created only when near the viewport; poster image first; shaders compiled and textures uploaded in the background |
| Page speed | LCP ≤ 2.5 s, CLS ≤ 0.1, INP ≤ 200 ms. `<canvas>` is not an LCP candidate, so the poster `<img>` usually is |

## 5. Quality tiers and fallbacks

`OrchidScene` classifies the GPU with `@pmndrs/detect-gpu`:

| Tier | Meaning | Serve |
|---|---|---|
| 0 | No WebGL, blocklisted or under 15 fps | Poster image only |
| 1 | ≥ 15 fps | Simplified scene: DPR 1, no post-processing, fewer particles, no shadows |
| 2 | ≥ 30 fps | Full scene, DPR ≤ 1.5 |
| 3 | ≥ 60 fps | Full scene, DPR ≤ 2, optional post-processing |

Also show the poster when: reduced motion is on (for scenes with camera movement), JavaScript fails, or the canvas hasn't mounted yet. drei's `PerformanceMonitor` lowers DPR further if frame rate drops at runtime.

## 6. Accessibility

- **Parallel semantic DOM.** Headings, text, links and buttons exist in the DOM next to the canvas, synced with it. Hide the mirror visually (`sr-only`), never with `display: none`.
- **Keyboard.** Every interaction has a keyboard path (buttons for rotate, next/previous; focusable hotspots mirrored in the DOM).
- **Motion.** No auto-playing camera flights; under reduced motion, a still. WCAG 2.2.2: anything moving for more than 5 s alongside content needs pause/stop. 2.3.1: no more than 3 flashes per second.
- **Canvas element:** `role="img"` with an `aria-label` describing the scene, or `aria-hidden="true"` when the DOM mirror carries everything.

## 7. Assets

Prefer, in order: the user's own models and screenshots; procedural geometry and shaders; CC0 libraries. See `references/imagery.md` for licences.

| Source | Licence | Good for |
|---|---|---|
| Poly Haven | CC0 | HDRIs, PBR textures, realistic props (glTF) |
| ambientCG | CC0 | Materials |
| Kenney, Quaternius, KayKit | CC0 | Stylised low-poly models |
| Smithsonian Open Access 3D | CC0 on marked models | Museum scans (heavy; decimate) |
| Poly Pizza | Mostly CC-BY | Low-poly props (credit the author) |
| Sketchfab | Per model | Check each licence |

Generate in code: geometry, shaders for known effects, particles, camera paths, 3D text. Source as assets: organic models, products, characters, photoreal materials, HDRIs.

## 8. Verification hooks

In development, or in builds made with `NEXT_PUBLIC_ORCHID_PROBES=1`, `SceneCanvas` exposes `window.__scene`, and `?orchid-tier=0..3` forces the quality tier (headless browsers have no GPU, so detection would always say tier 0):
```ts
window.__scene = {
  info: () => ({ calls, triangles, dpr, tier, running }),
  probes: [ { name: 'rotate-right', run: async () => {...}, check: () => boolean } ],
}
```
`check-page.mjs` reads `info()`, samples frame times and runs every probe. Write a probe for each interaction listed in `.orchid/3d.md`. This exists because screenshots can't distinguish a working scene from a broken one: in WorldCoder-Bench (2026), page-level checks were essentially uncorrelated with real correctness, and the dominant failures were broken interaction wiring, not missing objects.

## 9. Common agent mistakes

- Forgetting `dpr`, Draco/Meshopt decoders or KTX2 transcoder paths.
- Mixing `three` and `three/webgpu` imports (doubles the bundle).
- GLSL written for WebGPU, or TSL written for WebGL.
- Creating materials or geometries inside render loops; not disposing on unmount.
- Colour management: textures that carry colour need `colorSpace = SRGBColorSpace`; data textures (normal, roughness) don't.
- Rendering continuously when nothing changes (battery drain on laptops and phones).
- Canvas mounted on the server in Next.js: load scenes with `dynamic(() => import(...), { ssr: false })` and keep the poster server-rendered.
